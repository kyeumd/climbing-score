## 1. 목적

클라이밍장에서 완등한 문제를 **난이도 색깔 단위로 기록**하고, **본인의 숙련도 레벨과 문제 난이도의 상대적 차이**로 점수를 매겨 성장 추이를 보는 앱.

**주 사용 맥락은 "그 날 친구들과 하는 내기"다.** 같은 날·같은 짐에서 여러 사람이 완등을 기록하고 점수로 겨룬다. 기록은 그 부산물로 축적된다. 다중 프로필이 필요한 이유가 이것이므로, **당일 대결 스코어보드가 앱의 기본 화면**이 된다.

1차 목표는 **서버 없이 브라우저만으로 동작하는 정적 사이트**. 단, 나중에 서버·계정을 붙일 수 있도록 저장 계층과 클라이밍장 설정을 처음부터 분리한다.

### 비목표 (1차 범위 밖)

- 로그인·계정·서버 동기화 (같은 기기 한 대에 모여서 기록하는 것을 전제)
- 소셜 기능, 외부 공유, 전체 사용자 랭킹 (기기 안에서 끝난다)
- 개별 문제 단위 등록 (문제 이름·위치·사진)
- 시도 횟수, 플래시 보너스, 온사이트 구분

## 3. 사전 조사: 짐 목록과 색깔 체계

### 3.1 짐 목록 수집 — 서울 실내 113곳

정부 공공데이터에는 클라이밍장 통계가 **없다.** 인공암벽장업이 체육시설업 등록·신고 대상이 아니기 때문이다. 민간 출처를 차례로 뒤졌다.

| 출처 | 키 | 서울 수집분 | 결과 |
|---|---|---|---|
| 공공데이터포털 | 불필요 | 0 | 통계 자체가 없음 |
| climbing.kr | 불필요 | 0 | 사이트 폐쇄 |
| OpenStreetMap Overpass | 불필요 | 13 | 커버리지 부족 |
| climblife.co.kr | 불필요 | 53 | 누락 많음 (송파구 1곳 등) |
| **spiri7.com** | **불필요** | **98** | **채택** |

**스피릿(spiri7)이 결정적이었다.** 클라이밍 기록 앱의 공개 엔드포인트에서 전국 암장 889곳의 이름을 받고, 각 암장 페이지의 `__NEXT_DATA__`에서 id와 주소를 얻어 서울 볼더링장만 추렸다.

최종 **113곳 / 25개 구**. 결과는 `data/gyms.seed.json`.

**색 등급을 안 쓰는 암장을 구분한다.** 커버리지를 넓히려고 볼더링 필터를 뺐더니 지구력·리드 중심 암장이 섞여 들어왔다. 조사해 보니 14곳이 **색 등급 체계를 아예 쓰지 않는 곳**이었다.

| 암장 | 실제 체계 |
|---|---|
| Summit, 써니사이드 | 지구력 전용 (YDS 5.8~) |
| 볼더룸 | 문보드·킬터보드 (클라이밍 카페) |
| 권영세 | 테이프 색+번호는 등급이 아니라 문제 식별자 |
| 목동클라이밍센터 | 강습·지구력 중심 |

이런 곳을 "난이도 미등록"으로 적으면 데이터가 빠진 것처럼 읽힌다. 스피릿의 종목 정보(`exercises`)를 시드에 담아 **"지구력 중심"처럼 실제 성격을 표시**한다. 블로그 조사로 확인한 5곳이 모두 종목 정보와 일치했다.

그 결과 진짜 미상은 **1곳**뿐이다.

**볼더링 종목 필터를 걸지 않는다.** 스피릿에 볼더링이 등록만 안 된 짐이 통째로 빠지기 때문이다(그 필터 하나로 100곳에서 128곳으로 늘었다). 대신 야외 인공암벽장·대학·공공 체육시설은 이 앱의 대상이 아니므로 이름으로 걸러낸다.

**한계**: 이 목록도 완전하지는 않다. 사용자 등록 기반이므로 신규 개업이나 소규모 암장은 빠질 수 있다. **앱에서 직접 추가**하는 경로를 반드시 유지한다.

### 3.2 색깔 체계 수집 — 113곳 중 98곳(86%)

같은 스피릿에 등급 API가 있었다.

```
GET https://api.spiri7.com/api/v1/companies/gyms/{gymId}/skill?exerciseId=1
```

각 등급에 `match_level` 값이 있어 **쉬움→어려움 순서가 추정이 아니라 확정값**으로 나온다. 이전 방식(블로그 후기에서 색 순서를 읽어내기)은 성공률이 36%에 그쳤으나, 이 API로 86%를 확보했다.

**교차 검증**: 블로그 후기로 독립 확인한 4곳과 대조해 전부 일치했다.

| 암장 | 스피릿 | 블로그 후기 | 결과 |
|---|---|---|---|
| 정지현클라이밍짐 | 8단계 | 8단계 | 일치 |
| 드림캐처 클라이밍 | 9단계 | 9단계 | 일치 |
| 강서 클라이밍센터 | 9단계 | 9단계 | 일치 |
| 홍대클라이밍센터 | 8단계 | 8단계 | 일치 |

웹 검색으로는 끝내 못 찾던 **더클라임 체계도 확인됐다**: 흰색 < 노랑 < 주황 < 초록 < 파랑 < 빨강 < 핑크 < 보라 < 회색 < 갈색 < 검정 (11단계). 2025년 8월 개편으로 빨강과 보라 사이에 핑크가 신설됐고, 홍대B점만 숫자 1~9를 쓴다.

**단계 수 분포**: 5단계부터 11단계까지 제각각이며 9단계가 가장 흔하다. 평균 8.6단계.

### 3.3 확인된 사실

1. **색깔–난이도 대응에 표준이 없다.** 100곳 실측으로 확인했다.
   - **흰색**: 더클라임에서는 가장 쉬운 색, 서울볼더스에서는 보라 위의 상위 난이도
   - **회색**: 더클라임은 보라 위·갈색 아래, 클라임투더문은 **검정보다 위(최고 난이도)**
   - **빨강**: 피커스는 최하위, 더클라임은 6번째
   - 색 이름도 34종이 등장하며, 숫자(1~9)나 V등급을 쓰는 곳도 있다
2. **공통 축은 V스케일이다.** 대한스포츠클라이밍협회 기준:

   | 구분 | V등급 | 리드(YDS) |
   |---|---|---|
   | 입문자 | Vb, V0- | 5.7 ~ 5.9 |
   | 경력자 | V0 ~ V4 | 5.10a ~ 5.11c |
   | 고급경력자 | V5 ~ V10 | 5.12a ~ 5.13c |
   | 전문가 | V11 ~ V16 | 5.14 ~ 5.15+ |

3. **색 단계 수는 9~10단계**가 실측 기준 표준적이다.

### 3.4 설계에 미치는 결론

**수집한 색 체계는 전부 "미검증 초기값"으로 취급한다.** 근거:

- 출처 대부분이 개인 블로그이며 작성 시점이 불명확하다
- 암장은 세팅을 주기적으로 바꾼다
- 공식 출처로 교차 검증된 것은 서울숲 하나뿐이다

따라서 `Gym`에 `gradesVerified` 플래그를 두고, **미검증 짐을 처음 선택할 때 "이 색 체계가 맞나요?" 확인 배너**를 띄워 사용자가 확정·수정하게 한다. 확인 전까지는 초기값일 뿐이라는 것을 UI에서 숨기지 않는다.

**V등급은 점수 계산에 사용하지 않는다.** 5절 점수제가 짐 내부의 상대 순서만으로 성립하므로 사용자가 V등급을 몰라도 앱을 온전히 쓸 수 있다.

## 4. 데이터 모델

```
Gym {
  id             문자열, 불변
  name           "○○클라이밍 △△점"
  gu             "강남구" — 지역 칩 필터용 (D15: 주소·좌표는 담지 않는다)
  grades: [ Grade ]
  scoreTable     ScoreTable       점수표 (5절)
  favorite       불리언           ★ 즐겨찾기 — 상단 고정
  archived       불리언           삭제 대신 보관
  gradesVerified 불리언           사용자가 색 체계를 확인했는가 (3.4절)
  gradesSource   문자열 | null    초기값 출처. 사용자가 수정하면 null
  isCustom       불리언           사용자가 직접 추가한 짐인가
}

Grade {
  id            문자열, 불변 — 세션이 이 값을 참조한다
  label         "빨강", "노랑" 등 표시 이름
  color         화면 표시용 CSS 색상값 (#RRGGBB)
  order         정렬 순서. 0 = 가장 쉬움 = "1단계"
  retired       true면 신규 기록에서 숨기되 과거 기록은 유지
}

ScoreTable {
  mode          "formula" | "manual"
  baseScore     기준 점수. 기본 100
  upFactor      한 단계 어려울 때 배율. 기본 1.5
  downFactor    한 단계 쉬울 때 배율. 기본 0.5
  overrides     { "L{level}:{gradeId}": 점수 }   개별 칸 수동 수정분
}

Profile {
  id            문자열, 불변
  name          표시 이름
  level         정수 0~15. 이 사람의 숙련도
  primaryGymId  기본 선택될 짐. 즐겨찾기 중 하나
  createdAt     ISO 날짜
}

Session {
  id            문자열
  profileId     Profile 참조
  gymId         Gym 참조
  date          "YYYY-MM-DD" (로컬 날짜)
  levelAtTime   정수. 기록 시점의 내 레벨 스냅샷 (5.3절)
  counts        { [gradeId]: 정수 }
  memo          선택, 짧은 메모
}
```

### 설계 근거

- **세션은 gradeId를 참조하고 색상값을 복사하지 않는다.** 짐이 색 표시를 바꿔도 과거 기록의 의미가 유지된다.
- **Grade는 삭제하지 않고 `retired` 플래그를 세운다.** 암장이 세팅을 바꿔 색이 없어져도 과거 세션이 깨지지 않는다. 이 앱에서 가장 중요한 데이터 무결성 규칙이다.
- **레벨은 프로필당 하나다.** 숙련도는 사람에게 붙는 값이지 짐에 붙는 값이 아니다. 짐을 옮긴다고 실력이 달라지지 않는다. 짐마다 난이도 단계 수가 달라도 사용자는 그걸 감안해 자기 수준을 하나로 말한다. (초기 설계에서는 짐별 맵이었으나, 현실과 어긋나 단일 값으로 바꿨다. 예전 데이터는 짐별 값 중 최댓값으로 이전한다.)
- **레벨을 바꾸면 오늘 세션은 따라가고 지난 세션은 그대로다.** 오늘은 아직 진행 중인 기록이므로 새 레벨로 계산되어야 카드에 표시된 단가와 합계가 일치한다. 지난 날짜는 그때의 실력으로 남긴다.
- **날짜는 로컬 날짜 문자열.** 타임존 변환으로 "어제 세션"이 되는 사고를 막는다.

## 5. 점수 산정

### 5.1 기본 구조

점수는 **내 숙련도 레벨(L)과 문제 난이도 단계(d)의 차이**로 결정된다. 짐마다 별도의 점수표를 갖는다.

```
diff = d - L                       (d, L 모두 0부터 시작)

diff >= 0  →  score = round(baseScore × upFactor   ^  diff)
diff <  0  →  score = round(baseScore × downFactor ^ (-diff))
```

기본값 `baseScore=100`, `upFactor=1.5`, `downFactor=0.5`일 때:

|  | 1단계 | 2단계 | 3단계 | 4단계 | 5단계 |
|---|---|---|---|---|---|
| **LV0** | 100 | 150 | 225 | 338 | 506 |
| **LV1** | 50 | 100 | 150 | 225 | 338 |
| **LV2** | 25 | 50 | 100 | 150 | 225 |
| **LV3** | 13 | 25 | 50 | 100 | 150 |
| **LV4** | 6 | 13 | 25 | 50 | 100 |

반올림은 JS `Math.round` 기준(0.5는 올림)이다. 언어에 따라 0.5를 짝수로 내리는 구현이 있어 표 값이 1점 어긋날 수 있으므로 명시해 둔다.

- 대각선(내 레벨 = 문제 난이도) = 항상 `baseScore`
- 한 단계 어려운 문제 = 1.5배
- 한 단계 쉬운 문제 = 절반

**이 구조를 쓰는 이유**: 고수가 쉬운 문제를 다량 완등해 점수를 쌓는 걸 막고, 초보의 첫 상급 완등을 제대로 평가한다. 또 짐마다 대각선이 항상 `baseScore`로 정규화되므로, 색 체계가 다른 짐끼리도 점수 스케일이 맞아 합산이 성립한다.

### 5.2 표 편집

- 짐 설정 안의 **점수표 화면**에서 위 표를 그대로 보여준다.
- `baseScore` / `upFactor` / `downFactor` 세 값을 바꾸면 표 전체가 즉시 다시 계산된다.
- **개별 칸을 탭해 직접 수정**할 수 있다. 수정한 칸은 `overrides`에 저장되고 표에서 시각적으로 구분 표시한다. "공식으로 초기화" 버튼으로 되돌린다.
- 표 크기는 자동이다. 난이도가 8색이면 8열, 레벨은 LV0~LV7로 8행.

### 5.3 레벨 변경과 과거 기록

레벨은 사용자가 프로필에서 직접 설정한다(D8). 여기서 문제가 하나 생긴다.

> 레벨을 올리는 순간, 과거 세션을 현재 레벨로 재계산하면 지난 기록의 점수가 전부 쪼그라든다.

**해결: 세션에 `levelAtTime`을 스냅샷으로 저장한다.** 과거 세션은 그때의 레벨로 계산되어 값이 보존되고, 새 세션만 현재 레벨을 쓴다.

이 규칙 덕분에 다음 두 가지가 동시에 성립한다.

- 점수 자체는 저장하지 않고 **항상 원본 카운트에서 파생 계산**한다 → 공식(배율)을 바꾸면 과거 기록이 자동 재계산된다
- 계산의 **입력값인 레벨은 고정**된다 → 레벨을 올려도 과거 점수는 그대로다

세션 편집 화면에서 `levelAtTime`을 수동으로 고칠 수 있게 열어둔다(잘못 기록한 경우 대비).

**배율에는 유효 범위가 있다.** `upFactor` 1~5, `downFactor` 0.05~1, `baseScore` 1~100,000. 0을 넣으면 모든 칸이 최소값으로 뭉개져 난이도 구분이 사라지므로 입력·계산 양쪽에서 가둔다. 또 어떤 조합에서도 완등 1개는 최소 1점을 보장한다.

### 5.4 짐 간 합산은 하지 않는다 (D12)

**짐이 다르면 점수를 합치지 않는다.** 대각선 정규화 덕분에 스케일은 맞지만, 짐마다 세팅 난이도와 단계 수가 달라 합산 총점은 의미를 왜곡한다. 통계는 항상 **짐별로 분리**해 보여준다.

당일 대결도 같은 짐 안에서만 성립한다 — 서로 다른 짐에 있는 두 사람의 점수는 비교 대상이 아니다.

### 계층 규칙

- `domain/`은 DOM도 localStorage도 모른다. 순수 함수만. → 그대로 테스트 가능하고, 나중에 서버로 옮겨도 재사용된다.
- `ui/`는 `storage/`를 직접 호출하지 않고 `app.js`가 주입한 것만 쓴다.
- 서버를 붙일 때 **`storage/api.js`를 추가하고 `app.js` 한 줄만 교체**한다.

### 저장 계약 (adapter.js)

```
loadAll()            → { profiles, gyms, sessions }
saveProfile(p)       upsert
saveGym(g)           upsert
saveSession(s)       upsert
deleteSession(id)
exportJSON()         → 문자열
importJSON(text)     → 검증 후 전체 교체
loadSeed()           data/gyms.seed.json 최초 1회 적재
```

시드는 첫 실행 때만 적재하고 이후에는 사용자 데이터가 우선한다. 사용자가 수정한 짐을 시드가 덮어쓰면 안 된다.

`export`/`import`를 1차부터 넣는다. localStorage는 브라우저 데이터를 지우면 사라지므로, 백업 기능을 나중에 추가하면 **이미 기록을 잃은 뒤**가 된다.

## 7. 화면 설계

### 7.1 당일 대결 화면 (기본 화면, D11)

앱을 열면 여기가 뜬다. 오늘·기본 짐이 자동 선택된 상태다.

**상단** — 짐 선택기(★ 즐겨찾기 우선), 날짜. 짐이 미검증 색 체계면 확인 배너를 띄운다(3.4절).

**중단 — 스코어보드**. 오늘 이 짐에 기록 중인 프로필들이 점수 내림차순으로 나열된다.
- 1위 강조, 2위와의 점수 차를 함께 표시
- 각 행에 이름·현재 점수·완등 수·본인 레벨
- 순위가 바뀌면 행이 자리를 바꾸는 애니메이션(transform만 사용)
- "참가자 추가" 버튼 → 프로필 선택·생성

**하단 — 내 입력부**. 현재 선택된 프로필의 등급 카드 그리드.
- 카드 **탭 → +1**, 길게 누르기 또는 − 버튼 → −1
- 각 카드에 카운트와 현재 레벨 기준 단가 점수
- 내 레벨과 같은 단계 카드에 기준선 표시
- 참가자가 여럿이면 상단 스코어보드에서 이름을 탭해 입력 대상을 전환

한 손 조작 전제로 탭 타겟 최소 44px, 입력부는 화면 하단 절반에 배치한다.

**하루 여러 세션 처리**: `프로필 + 짐 + 날짜` 조합당 세션 1개. 같은 날 같은 짐 재방문은 기존 세션에 누적, 같은 날 다른 짐은 별도 세션.

### 7.2 짐 선택기 (D14)

- 최상단에 **★ 즐겨찾기** 줄
- 그 아래 **구 칩 가로 스크롤** — `전체 · 강남구 · 영등포구 · 종로구 …` 짐 수가 많은 구부터 정렬. 17개 구
- 칩 선택 시 해당 구 짐만 목록에 표시
- 이름 검색 입력란 병행
- 목록 맨 아래 **"직접 추가"** — 시드 목록이 완전하지 않으므로(3.1절) 필수 경로다
- 색 체계가 없는 짐(29곳)은 목록에서 표시로 구분하고, 선택 시 등급 설정 화면으로 유도

### 7.3 통계 화면

**짐별로 분리해 보여준다(D12).** 짐을 하나 고르면:

- 그 짐에서의 누적 점수, 세션 수, 최고 완등 단계
- 최근 N회 세션 점수 추이 (인라인 SVG 스파크라인, 라이브러리 없음)
- 단계별 누적 완등 수
- 대결 전적 — 과거 당일 대결의 승패 누적. 그 짐에서 함께 기록한 프로필에 한정
- 최근 세션 목록 → 탭하면 수정

### 7.4 프로필 화면

프로필 추가·이름 변경·전환·삭제. **짐별 내 레벨 설정**. 기본 짐 지정. JSON 내보내기/가져오기.

### 7.5 짐 설정 화면

짐 이름·구 편집, **★ 즐겨찾기 토글**. 등급 행 추가·삭제(retire)·순서 변경, 색상 지정. **"색 체계 확인 완료"** 토글(`gradesVerified`). 점수표 편집 화면 진입.

**이 화면이 3.4절 결론의 구현체**다. 46곳 중 29곳은 색 체계가 비어 있고 나머지 17곳도 미검증이므로, 이 화면 없이는 앱이 성립하지 않는다.

### 7.6 점수표 편집 화면

5.2절 참조. 레벨 × 난이도 격자, 배율 3개 조정, 개별 칸 수동 수정, 공식 초기화.

## 8. 디자인 방향

`soft-skill`(high-end-visual-design) 적용. 스킬이 요구하는 아카이타입 선택 결과:

- **Vibe: Ethereal Glass** 기반, 단 시스템 테마에 따라 라이트/다크 2셋 운용(D9)
- **Layout: Asymmetrical Bento** — 통계 화면에 적용. 대결 화면은 스코어보드 + 등급 그리드 2단 구성

### 8.0 난이도는 색과 모양으로 이중 부호화한다 (D16)

색만으로 난이도를 구분하면 색각이상자는 앱을 쓸 수 없다. 실제 클라이밍 홀드 8종(저그·슬로퍼·핀치·크림프·포켓·엣지·볼륨·언더클링)을 실루엣으로 만들어 등급 순서마다 다른 모양을 배정한다. 볼트 구멍을 하나 뚫어 실제 홀드임을 드러낸다.

**외곽선은 색 자체의 밝기로 정한다.** 테마 대비색 하나로 고정하면 흰색은 라이트에서, 검정은 다크에서 배경에 묻힌다(측정값 1.08:1). 상대 밝기를 계산해 밝은 색은 어두운 선, 어두운 색은 밝은 선으로 감싼다.

이 결정은 접근성만이 아니라 성격도 만든다. 짐마다 홀드 조합이 달라 목록에서 한눈에 구별된다.

### 8.1 색깔 예산 규칙 (본 프로젝트 고유 규칙)

soft-skill의 절제된 팔레트 요구와 "난이도 색깔이 핵심 정보"라는 요구가 정면 충돌한다. 다음 규칙으로 해소한다.

> **채도는 오직 난이도 색깔에만 배정한다. UI 크롬(배경·카드·텍스트·버튼)은 완전한 무채색을 유지한다.**

- 등급 카드를 색으로 **가득 칠하지 않는다.** 카드 위에 색 링·도트·좌측 4px 바로 표현한다
- 색이 들어간 요소끼리 인접시키지 않는다. 카드 사이 간격을 넓게 둔다
- 강조·성공·경고 상태에 별도 색을 쓰지 않는다 — 난이도 색과 경쟁하기 때문
- Ethereal Glass가 요구하는 배경 메시 그라디언트도 **무채색으로 제한**한다. 스킬이 예시로 든 보라·에메랄드 발광 오브는 난이도 색과 충돌하므로 쓰지 않는다

### 8.2 양쪽 테마에서의 색 대비 (D9의 실제 비용)

시스템 테마를 따라가므로 **난이도 색 식별성을 라이트·다크 양쪽에서 각각 보장**해야 한다. 서로 반대 방향의 문제가 생긴다.

- **다크 배경**: 검정·남색·갈색 등급이 배경에 묻힌다
- **라이트 배경**: 흰색·노랑·베이지 등급이 배경에 묻힌다

**대응**: 모든 색 도트에 **테마 대비색 hairline 링**을 두른다(다크에서 흰색, 라이트에서 검정, 각각 낮은 불투명도). 색 도트는 절대 배경 위에 맨몸으로 놓지 않는다. 이 규칙 하나로 양쪽 문제가 동시에 해결된다.

### 8.3 스킬 규칙 적용 방식

바닐라 CSS 환경이므로 스킬의 Tailwind 클래스는 동등한 CSS로 번역한다. 원칙은 그대로 지킨다.

| 스킬 요구 | 바닐라 구현 |
|---|---|
| Double-Bezel 중첩 구조 | 외곽 셸 + 내부 코어 두 겹, 동심 반경 `calc()` |
| 커스텀 cubic-bezier | `--ease-spring: cubic-bezier(0.32,0.72,0,1)` 토큰화 |
| 스크롤 진입 애니메이션 | `IntersectionObserver` (스킬이 scroll 리스너를 금지) |
| transform/opacity만 애니메이트 | GPU 안전. `top/left/width/height` 금지 |
| backdrop-blur는 고정 요소만 | 하단 점수 바와 모달에만 적용 |
| `min-h-[100dvh]` | iOS Safari 뷰포트 점프 방지 |
| 금지 폰트 (Inter/Roboto/Helvetica/Arial) | **Plus Jakarta Sans** (Google Fonts) + 시스템 폴백 |
| 금지 아이콘 라이브러리 | SVG를 인라인으로 직접 작성 — 의존성 0 유지 |
| 라이트/다크 | `prefers-color-scheme` + CSS 변수 2셋 |

점수 숫자가 실시간으로 바뀌므로 모든 수치 표시에 `font-variant-numeric: tabular-nums`를 적용해 자릿수 흔들림을 막는다. 점수표 격자에도 동일 적용.

### 8.4 모션 수위 조정

스킬은 시네마틱 모션을 요구하지만, 본 앱은 **암장에서 빠르게 탭하는 상황**이 주 사용 맥락이다. 랜딩페이지 수준의 스크롤 연출은 사용성을 해친다.

- 대결 화면: 탭 피드백(스프링 스케일 `0.98`), 점수 롤업, 순위 교체 시 행 이동. 진입 애니메이션 없음
- 통계 화면: 스크롤 진입 페이드업 허용
- 화면 전환: 200ms 이내

## 11. 검토 방법 (실제로 겪은 실패에서 나온 것)

자동 검사가 "0건"이라고 해서 넘어갔다가 눈에 보이는 문제를 여러 번 놓쳤다. 원인은 네 가지였고, 각각 대책을 도구에 박아 넣었다.

| 원인 | 무슨 일이 벌어졌나 | 대책 |
|---|---|---|
| 캐시 | 서버가 `Cache-Control`을 안 보내 브라우저가 옛 CSS를 씀. **고쳐도 화면이 그대로** | `tools/dev-server.py` (no-store) |
| 브라우저 프로필 공유 | 검사용 Chrome이 같은 `user-data-dir`을 써서 두 번째 실행이 기존 브라우저에 붙음. **옛 페이지를 검사** | 실행마다 프로필·포트 분리 + CDP 캐시 끄기 |
| 뷰포트 단일 | 414×896만 검사. 문제는 360×640에서만 발생 | 뷰포트 3종 |
| 기하 추정 | `getBoundingClientRect`로 클리핑 여부를 *추정*. 가정이 틀리면 조용히 놓침 | `document.elementFromPoint`로 브라우저에 직접 질의 |

그리고 자동 검사만으로는 부족하다. 규칙에 없는 추함은 통과한다. **마지막 판정은 눈으로 한다.**

```bash
npm run review          # 화면·모달 22종을 한 장의 컨택트 시트로
npm run review:light    # 라이트 테마
npm run review:small    # 360x640
npm run flow            # 상호작용 흐름 7종을 스텝별 스트립으로
```

`flow`가 잡아낸 대표적인 버그: 숙련도를 올렸을 때 **카드에 표시된 단가와 세션 합계의 계산 기준이 어긋난 것.** 두 화면 각각은 멀쩡해 보여서 정지 화면으로는 나오지 않았다.

화면이 수십 개라 한 장씩 열면 감당이 안 되므로 격자 한 장으로 합쳐 훑고, 이상한 칸만 원본으로 확대한다. 페이지별로 검토를 나눠 맡기면 한 사람(또는 한 컨텍스트)이 다 보지 않아도 된다.

## 12. 구현 순서

1. `domain/scoring.js` — 점수표 생성·조회 함수. 의존성 없으므로 먼저, 테스트와 함께
2. `domain/gym.js`, `domain/session.js`, `domain/match.js` — 집계·순위 로직
3. `storage/adapter.js` + `local-storage.js` — 저장 계약과 구현, 시드 로딩
4. `styles/tokens.css` — 디자인 토큰 확정 (8절 규칙, 라이트/다크 2셋)
5. 짐 선택기 + 짐 설정 + 점수표 편집 — **색 체계 없이는 앱이 성립하지 않으므로 UI 중 최우선**
6. 프로필 화면 (레벨 설정 포함)
7. **당일 대결 화면 — 앱의 심장**
8. 통계 화면 (짐별)
9. JSON 내보내기/가져오기
10. 정적 배포 (선택)

1~3은 화면 없이 검증 가능하므로 테스트 우선으로 진행한다.
